# Resolve-Then-Stream Connector Ports with Chunked Write Sessions

Data Spark's connector ports (ADR-0029) move to a resolve-then-stream contract. `Source::read` takes the load's schema directive, the effective chunk bound, and the rejection sink, and returns the resolved facts — the schema decision, the pinned schema write, source bytes, full-input record counts — plus a lazy chunk iterator that materializes `RecordBatch` chunks of at most the bound in surviving records; a load whose surviving record run is empty still yields one empty chunk, so an empty dataset materializes its schema. Two-pass execution (ADR-0045) is the `local_file` implementation strategy behind the port, not the port contract: a future source that resolves its schema in one pass — a database with a catalog, a Parquet file with footer metadata — fits without pretending to have two. `Destination` becomes session-based: `begin(mode)` performs the mode's destination-side preparation (staging directories, connections, destination-schema inspection) and returns a writer with a write-chunk operation, an explicit `commit` returning the destination-owned write facts, and an `abandon` reporting the already-committed state when the source side fails mid-stream; dropping an uncommitted writer cleans up its staging state. Write facts stay destination-owned (ADR-0021), and the write-failure type keeps carrying facts plus written records, now joined by the committed chunk count so failure reports can state `batch_count` honestly (ADR-0047).

The chunk bound is load-definition configuration: a new optional top-level `execution` block, `execution: { chunk_rows: <integer >= 1> }`, defaulting to 65536 — large enough that small loads execute as today's single chunk, small enough to bound peak memory on large ones — wherever the block or the key is absent (`execution: {}` declares nothing and defaults like an absent block). Unknown keys inside the block are rejected recursively (ADR-0037), and `chunk_rows: 0`, negative, and non-integer values are definition failures at YAML parse time — the bound deserializes as a nonzero unsigned integer, so every invalid bound fails under the existing `invalid_load_definition_yaml` code and chunked execution introduces exactly one new failure code overall (`source_changed_during_load`, ADR-0045). The block is the future home for execution-behavior settings — retry policy and parallelism land here — and nothing else lives in it yet. The report's `execution` object echoes the effective bound as an additive `chunk_rows` field, with `report_version` unchanged (additive precedent: ADR-0030's top-level `dataset`).

Alternatives rejected: a byte-based chunk bound (rows are the unit validation, rejection, and Arrow materialization already speak; a byte bound would split records unpredictably across value widths); returning a materialized batch list instead of a lazy iterator (holds every chunk at once, forfeiting exactly the bounded peak the change exists for); putting `chunk_rows` under `source` or `destination` (the bound governs how the load executes, not where data comes from or goes, and the retry/parallelism settings joining it later are execution-scoped too); a push-based writer callback API (the pull-based iterator keeps the orchestrator the only control loop, so commit boundaries and failure attribution stay in one place).
