# Dispatch Chunk Writes Through a Bounded Window Capped by Per-Mode Connector Limits

Load parallelism (ADR-0023) lands as a **bounded window of concurrent chunk writes**: a load may hold up to an effective parallelism of `write_chunk` operations in flight at once, dispatched onto scoped worker threads by the write-phase dispatcher. Source chunk pulls stay strictly sequential and in stream order — only destination writes run concurrently — so the two-pass source contract (ADR-0045) and its mutation guard are untouched. The dispatcher pulls the next chunk only when a write slot is free, and the pulled chunk immediately occupies that slot, so at most window-many chunks are materialized simultaneously: peak memory scales as parallelism × `chunk_rows`, a product the user owns with no cross-field validation. At effective parallelism 1 the dispatcher is today's sequential loop, observably end to end — the path every load in the shipped connector matrix takes.

The cap is destination-owned: the `Destination` port declares a **Connector Parallelism Limit per load mode**, defaulting to the always-safe serial 1, and the engine never runs more than the mode's limit regardless of configuration (ADR-0052). Declaring a limit above 1 carries a declaration obligation mirroring ADR-0048's transience rule: a connector may declare it only when concurrent `write_chunk` completions cannot break that mode's documented commit semantics — append's committed-prefix visibility (ADR-0047), full refresh's nothing-visible-before-terminal-commit. The engine enforces only the window bound and never reasons about commit semantics itself. Structurally, `write_chunk` takes a shared writer reference (the session trait is `Sync`) and each writer owns whatever interior synchronization its declared limit needs — an uncontended lock at limit 1. **No shipped connector declares a limit above 1**, so the shipped matrix is provably serial — statically verifiable, since no override of the default exists outside test connectors.

Failure semantics are drain-then-abandon: when any in-flight unit fails terminally — immediately-terminal, or transient with budget exhausted — the dispatcher stops dispatching new chunks, lets already-in-flight writes run to completion (no preemption), then abandons the session, so committed facts stay destination-owned through the abandon path exactly as a serial source failure's. The surfaced failure is the terminal failure with the **lowest chunk index** — deterministic, never wall-clock completion order — with its code and message unchanged and no wrapper. A source-side pull failure mid-stream drains and abandons the same way; every dispatched write failure indexes below the halted pull position, so lowest-index needs no tie-break against it. Each in-flight unit retries independently inside its slot with its own per-unit budget and backoff sequence (ADR-0049 unchanged); a backoff wait occupies only that unit's slot and never pauses siblings, and the injectable sleeper contract is preserved so the test suite performs zero real sleeping — window tests synchronize through explicit rendezvous, no sleeps, no timing assertions.

Alternatives rejected: source-read, transform, or pass-level parallelism (the sequential two-pass source contract is the correctness anchor of resolve-then-stream; writes are where connector latency lives); a global engine-owned safety judgment (the orchestrator cannot know what a concurrent completion does to a connector's commit semantics — the originator-owned rule of ADR-0048 already settled where such knowledge lives); surfacing the first failure in wall-clock order (nondeterministic reports under identical inputs, exactly what the deterministic-report contract exists to prevent); preempting in-flight writes on failure (cancellation mid-write is the one way to manufacture partial-write uncertainty the safety model otherwise excludes); raising any shipped connector's limit above 1 now (a future connector or a separate decision does that, with the declaration obligation in force).
