# Split Timestamps Into Wall-Clock and UTC-Instant Types

Data Spark declares timestamps as two types split by offset discipline, both stored in microseconds. `timestamp` is a wall-clock datetime that states what a clock read without identifying an instant — Arrow `Timestamp(Microsecond, None)`, DuckDB `TIMESTAMP`, Parquet `TIMESTAMP(MICROS, isAdjustedToUTC=false)` — and its text must not carry an offset. `timestamptz` is a UTC instant — Arrow `Timestamp(Microsecond, "UTC")`, DuckDB `TIMESTAMPTZ`, Parquet `TIMESTAMP(MICROS, isAdjustedToUTC=true)` — and its text must end in `Z`/`z` or `±hh:mm`, with every offset normalized to the UTC instant it spells at parse time, so different spellings of one instant store equal values. Both types accept one strict menu: a four-digit year, zero-padded fixed-width fields, `YYYY-MM-DD`, one space or `T`/`t` separator, `HH:MM:SS`, and an optional fraction of 1 to 6 digits. Everything else rejects per record with the cause named: an offset present under `timestamp`, an offset absent under `timestamptz`, more than 6 fractional digits (rejection, never truncation), date-only text, epoch numbers — including JSON numbers, which never fit a timestamp field — leap-second text, and every locale-dependent form (month names, D/M/Y order). Alternatives rejected: one timestamp type with an optional offset (silently conflates wall-clock and instant semantics — a reader of the dataset cannot know whether `09:00` meant a local reading or a UTC moment); nanosecond storage (DuckDB's `TIMESTAMP` is microsecond-native, so nanoseconds would truncate at the destination after validation promised exactness); accepting epoch numbers (guessing the unit between seconds, milliseconds, and microseconds is the same class of silent corruption as locale guessing); per-field format strings and a `date` type (deferred to future issues rather than widening this slice's contract).
