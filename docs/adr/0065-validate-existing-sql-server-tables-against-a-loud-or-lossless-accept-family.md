# Validate Existing SQL Server Tables Against a Loud-or-Lossless Accept Family

Because the loader does not own production tables, every load mode that meets an existing table — append, merge, and full refresh alike, since ADR-0064's full refresh preserves the table object — validates the table at session begin, before any row is written, and fails with the new write-phase code `incompatible_destination_table`, listing every violation at once. The accept family for a mapped column is cut along one line: a column is acceptable when misfits are either impossible or loud, never silent. That admits the created shape (ADR-0062) itself; the lossless widenings `DATETIME2(7)` and `DECIMAL` of wider precision at the same scale; and the loud-failing narrower types `INT`/`SMALLINT`/`TINYINT` (overflow raises), `NVARCHAR(n)` (over-length raises under default ANSI settings), and `DECIMAL` of narrower precision at the same scale — under ADR-0062's principle that representability misfits are write failures, never Rejected Records. Silently-lossy shapes are excluded by default, and exactly one family is admissible by explicit signature: the legacy datetime columns production actually holds — `DATETIME` (~3.33 ms rounding) and `DATETIME2(p<6)` — via the destination-level boolean `accept_datetime_rounding: true` (default `false`), echoed as written through `destination_summary` (ADR-0060/0061) so every report carries the signature. `SMALLDATETIME`, `REAL`/`FLOAT(24)`, `VARCHAR` (silent code-page substitution), `DECIMAL` scale mismatches (the server rounds without error), `DATE`, `TIME`, and `DATETIMEOFFSET` stay unacceptable at any setting. Nullability mirrors the DuckDB rule: a `NOT NULL` column cannot receive a nullable field.

The column-set and constraint rules preserve dataset values while letting SQL Server supply extra columns. The pinned fork's `bulk_insert_with_columns` API (ADR-0069, #161) selects and sends only mapped columns, in the same order in its metadata query, `INSERT BULK` declaration, and row stream; Data Spark uses destination catalog order. Extra table columns outside the dataset are accepted iff nullable, `IDENTITY`, or `NOT NULL` with a `DEFAULT`: they are omitted, so the server supplies NULL, the default, or an identity. An extra `NOT NULL` column without a default is rejected, and merge's `INSERT` branch omits extra columns for the same net semantics. The bulk API still exposes no `KEEPNULLS` or `KEEPIDENTITY`. For mapped columns the hazard is value substitution, which is different in kind from rounding and therefore never behind the opt-in: an `IDENTITY` column is rejected on append and full refresh (the bulk path silently discards dataset values and assigns its own) but accepted on merge iff it is a merge key — `UPDATE` never touches keys, and the `INSERT` branch runs under ADR-0064's `SET IDENTITY_INSERT` wrap — while a non-key mapped `IDENTITY` stays rejected everywhere (`UPDATE` of an identity column always raises). A `DEFAULT`-carrying mapped column is rejected on append and full refresh when the dataset field is nullable (the bulk path cannot deliver a faithful `NULL`) and accepted when the field is `NOT NULL` or the mode is merge, whose regular DML preserves explicit `NULL`.

Consequences: additive drift stays pin-only — no `ALTER TABLE` — so a drifted dataset against an unmigrated table fails validation until the DBA adds the column; and because full refresh preserves the table object, drift on SQL Server materializes only through table creation or DBA migration, unlike DuckDB, whose full refresh recreates the table. Schema migration is a deliberate DBA act, not a load side effect. Alternatives rejected: exact created-shape-only acceptance (DuckDB's rule — it would bar the production tables this cycle serves); blanket widening (silent corruption by default); per-field opt-in granularity (the hazard is type-keyed, not field-keyed); an enum compatibility knob (one boolean per hazard keeps each signature explicit); materializing drift via `ALTER TABLE ADD` and retrofitting `incompatible_destination_table` onto DuckDB (both future work); and append/full-refresh support for mapped `IDENTITY` columns, to revisit only if tiberius exposes a `KeepIdentity` option.


Bulk column selection verified (2026-09-07, #136/#161). The original placeholder explanation was disproved by live tests: an extra `INT NOT NULL DEFAULT 42` cannot receive the driver's `I32(None)` against fixed-length metadata, and extra nullable `MONEY`, `SMALLMONEY`, and `SQL_VARIANT` cannot all be represented by placeholders. `IDENTITY` metadata is already non-updateable and filtered by the original driver rather than consuming a placeholder. The maintainer authorized a minimal fork API instead of narrowing the Accept Family. Its metadata query must also omit extra columns: `SELECT TOP 0 *` encounters unsupported `SQL_VARIANT` metadata before filtering. Live tests now prove omitted defaults/nulls/identities, selected NULL/default substitution, identifier quoting, selected column order, and transaction rollback. The Accept Family and mapped DEFAULT/IDENTITY restrictions above remain unchanged.
