# Land All Load Modes on SQL Server with Object-Preserving Write Strategies

The SQL Server destination supports all three load modes, widening ADR-0057's merge scope from DuckDB-only to DuckDB and SQL Server (every other destination still declines with `unsupported_load_mode_for_destination`). The strategies are chosen around one fact of the environment this cycle serves: production tables are owned by their environment, not by the loader, so a load must never replace the table object and silently shed its indexes, permissions, triggers, foreign keys, or defaults. Full refresh therefore runs as one explicit transaction on the load's single connection — `BEGIN TRAN`, `DELETE FROM` the target (or `CREATE TABLE` in the created shape of ADR-0062 when the table is missing — the only mode that bootstraps a table), one `bulk_insert` per chunk, terminal `COMMIT` — reported as `atomic` / `transactional_delete_insert`. Bulk load inside a user-defined transaction is documented TDS behavior and rolls back with it, and ADR-0056's mirror semantics hold: a zero-survivor full refresh commits an empty table. Append mirrors ADR-0047 verbatim: one `bulk_insert` call per chunk (one `INSERT BULK` batch), auto-committed, so a failed load keeps its committed prefix; reported as `best_effort` / `bulk_insert`, and the table must already exist. Both strategy strings are new; the report contract's version-1 compatibility clause admits them additively.

Merge is ADR-0059's staged terminal transaction in SQL Server idiom, reported as `atomic` / `transactional_merge` with the same merge counts. Inside `BEGIN TRAN`: create a real staging table `data_spark_merge_stage_<uuid>` in the target's schema — shaped by the dataset's created shape, deliberately not a clone of the target, so the bulk path always writes ADR-0062 types and any accepted lossy conversion happens server-side inside `MERGE`, governed by ADR-0065's opt-in — then bulk each chunk into the stage, run the ADR-0058 `duplicate_merge_keys` gate, count `updated` as staged rows with a key match in the target (`inserted = staged - updated`, preserving the documented `updated + inserted == written` invariant), execute `MERGE INTO <target> WITH (HOLDLOCK) … WHEN MATCHED THEN UPDATE` non-key columns (omitted when every column is a key) `WHEN NOT MATCHED THEN INSERT`, drop the stage, and `COMMIT`; any failure issues an explicit `ROLLBACK`. The in-transaction stage vanishes on rollback or connection death, so no orphan cleanup exists. When the merge key maps to an `IDENTITY` column — the production pattern that motivated it — the `MERGE` is wrapped in `SET IDENTITY_INSERT <target> ON/OFF` inside the terminal transaction so inserted keys land faithfully; this requires ALTER permission on the target table, and the session-scoped setting cannot leak because failure paths end the session. The target must already exist; merge never bootstraps a table.

Target-side duplicate merge keys get no gate: every destination row matching a staged key tuple is replaced whole, and counts stay source-perspective — the same behavior DuckDB's engine exhibits (its `MERGE` plans as a join with no cardinality error; SQL Server's error 8672 guards only the source-side multiplicity the ADR-0058 gate already removes), documented in the merge guide rather than defended against. Counting target-side via `OUTPUT $action` was rejected because a duplicate-keyed target would break the `updated + inserted == written` invariant. Alternatives rejected: a staged `sp_rename` swap for full refresh (near-instant cutover, but it replaces the table object and strips the legacy table's permissions, indexes, triggers, and foreign keys — and `ALTER SCHEMA … TRANSFER` documentedly drops permissions outright); `TRUNCATE` (blocked by inbound foreign keys, reseeds identity, needs ALTER); a terminal transaction for append (ADR-0047 already rejected staged append); and declining merge the way Parquet does (the production tables motivating this cycle receive merges).
