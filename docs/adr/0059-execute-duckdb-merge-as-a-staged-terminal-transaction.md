# Execute DuckDB Merge as a Staged Terminal Transaction

A DuckDB merge session executes as stage-then-merge inside one explicit transaction with a single terminal commit — the full-refresh commit family of ADR-0047, not append's per-chunk family. `begin` probes the destination table with a `LIMIT 0` select — the table must exist; a missing table fails `destination_write_failed` with "before merge" wording and the pre-write report posture, exactly like append, so bootstrap stays "first load `full_refresh`, then switch to `merge`" and no accidental table is ever created. The session then opens a transaction and creates a session-unique temporary staging table cloned from the destination's schema; every chunk aligns against the destination schema under the append rule verbatim (1:1 name match, exact types, non-nullable columns admit no nulls — additive drift against an unmigrated table fails at alignment) and inserts into the stage. `commit` runs the duplicate-key gate (ADR-0058), counts the staged records whose key tuple matches an existing destination record, executes one `MERGE INTO ... WHEN MATCHED THEN UPDATE SET <every non-key column> WHEN NOT MATCHED THEN INSERT`, and commits. Nothing is destination-visible before that commit; any earlier failure drops the connection, rolling the transaction back and discarding the stage, so a failed merge leaves the destination byte-identical. Matched records are replaced whole — every non-key dataset column takes the source value; with every column a key the matched clause is omitted, a matched record being its own replacement. The bundled engine (DuckDB 1.5.4) executes `MERGE INTO`; the contract locks these semantics, not the SQL spelling — an equivalent delete-plus-insert inside the same transaction would satisfy it.

The report gains only additive facts under the version-1 compatibility clause: `atomicity: "atomic"`, `strategy: "transactional_merge"`, and — on success only — `destination_write.merge: {"updated": M, "inserted": N}`, where `updated` counts matched-and-replaced records, `inserted` the unmatched remainder, and `updated + inserted == row_counts.written` holds by construction (the counts partition the stage, and the stage holds exactly the surviving records). The counts are measured inside the same transaction snapshot the MERGE runs under, as one aggregate — never per-row `RETURNING`, which would materialize unbounded results. A zero-survivor merge stages nothing, merges nothing, commits, and exits `0` — the ADR-0056 mirror posture, with the rejection route still guarded by `reject_threshold`. Every raising site classifies `Transience::Terminal` (ADR-0048's uncertainty rule: mid-transaction re-attempts are not provably uncommitted units), keeping `retry:` legal and inert, and the connector's parallelism limit stays the default serial 1 (ADR-0051), so the shipped matrix remains provably serial.

Alternatives rejected: merging each chunk directly from the Arrow table function (a per-chunk `MERGE` is a per-chunk commit — append's family — breaking the terminal promise, and cross-chunk duplicate keys would be undetectable); `INSERT ... ON CONFLICT` (requires a primary-key or unique constraint on the destination, which tables bootstrapped by `full_refresh` do not have, and would silently bind the mode to physical constraints instead of the declared keys); counting `updated`/`inserted` via `MERGE ... RETURNING` (per-row results, unbounded memory for exactly one pair of integers); a fixed stage name without session uniqueness (a user dataset of the same name could capture unqualified references; the stage is referenced through the connection-local `temp` catalog and carries a per-session suffix).
