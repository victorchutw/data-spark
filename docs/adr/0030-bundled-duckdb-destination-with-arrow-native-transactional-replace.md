# Bundled DuckDB Destination with Arrow-Native Transactional Replace

Data Spark will add a `duckdb` destination connector behind the ADR-0029 `Destination` port using the `duckdb` crate with the `bundled` feature, statically compiling the DuckDB engine into the single release binary (ADR-0001 / ADR-0025) at an accepted build-time and binary-size cost. The materialized Arrow batch will be ingested through the crate's `vtab-arrow` path: the connector registers the batch behind the `arrow(?, ?)` table function and executes one `CREATE OR REPLACE TABLE "<dataset>" AS SELECT * FROM arrow(?, ?)` statement, so Arrow-to-DuckDB type mapping is delegated to DuckDB's own Arrow import and the full refresh commits as a single implicit transaction: the new table becomes visible completely or the old table is left untouched (an Atomic Commit per `CONTEXT.md`), with no explicit `BEGIN` / `COMMIT` wrapper until a multi-statement load mode needs one. A DuckDB destination will be addressed by `destination.path` naming the `.duckdb` database file and the previously dormant top-level `dataset` field naming the table, which the load report will echo as an additive top-level `dataset` field (`null` when absent, report version unchanged); `dataset` will be required for `duckdb` and validated in the pure `destination_connector` factory (failure code `missing_dataset`), which amends ADR-0029's "connector name only" factory contract to "connector name plus addressing completeness" while staying free of I/O (ADR-0019). The table identifier will always be wrapped in double quotes with embedded double quotes escaped by doubling (`"` becomes `""`), rather than restricted to a character allowlist, and tables will land in DuckDB's default `main` schema. The write will report `atomicity: "atomic"` and `strategy: "transactional_replace"` (ADR-0021) — the first destination to exercise destination-reported write facts beyond Parquet's `best_effort` / `staging_then_replace`; no new `CONTEXT.md` vocabulary is needed because Atomic Commit already names the behavior. Because a database table has no honest per-table byte count, `DestinationWrite::bytes_written` will widen to `Option<u64>` with DuckDB reporting `None` (`byte_counts.destination: null`, already nullable in the report), realizing on the write side the "byte counts are not universal" evolution ADR-0029 anticipated for `source_bytes`; Parquet will keep reporting its measured directory bytes.

Accepted consequences:

- The `arrow-array` / `arrow-schema` / `parquet` dependencies will move from 59.1 to 58.3 to match the `duckdb` crate's `arrow ^58` pin, and Arrow upgrades will follow duckdb-rs's cadence until it tracks the current Arrow major.
- Clean builds will compile the bundled DuckDB engine: several extra minutes per uncached CI run and tens of megabytes on the release binary. Build caching is deferred until it hurts.
- Concurrent loads into the same `.duckdb` file will contend on DuckDB's database file lock, and the loser will fail with `destination_write_failed` — unlike Parquet's staging-token concurrency, which lets concurrent loads race to the final rename.
