# Report Retry as a Policy Echo with Per-Failed-Attempt Entries

The load report's `execution` object gains an additive `retry` object: the effective policy echo — `max_attempts`, `initial_delay_ms`, `max_delay_ms`, resolved defaults included — plus an `attempts` array. The presence rule follows the write-phase postures of ADR-0047: the `record_format: "arrow_record_batch"` postures — success and in-session failures — **always** carry `retry`, with zero attempts represented as an always-present empty array; the `"not_started"` posture carries `retry` **only when the attempts array is non-empty**. Today that is provably never — no shipped failure is transient (ADR-0048), so every current `not_started` report stays byte-unchanged — and the rule materializes only when a future connector classifies `begin` failures transient and exhausts them, keeping ADR-0022's every-attempt-visible guarantee without pretending records were exchanged.

The `attempts` array records **one entry per failed attempt of a retried unit, including the final failure** — terminal or exhausted — so the report counts directly how many times the unit was tried; successful attempts are not recorded, and a unit the engine never retried (an immediately-terminal failure, or `max_attempts: 1`) records nothing, which is what keeps never-retried failure reports byte-identical. Each entry states `operation` (`"begin"` or `"write_chunk"`), the 0-based `chunk_index` in the stream (absent for `begin`), the 1-based `attempt` within the unit, an `error` mirroring the `error_summary` shape, and `delay_before_retry_ms` — the wait applied after this failure, absent exactly when no retry followed. On exhaustion the load's `error_summary` is the last attempt's failure unchanged; the attempts array tells the retry story around it. Deliberately not recorded: per-attempt timestamps (load-level `timings` plus the recorded delays cover delay diagnosis) and per-attempt commit certainty (the safety model already guarantees retried attempts committed nothing, and the final failure's commit state is told by `batch_count`, `row_counts`, and `destination_write`). `report_version` stays `1`: everything is additive (the ADR-0030 and ADR-0046 precedent).

Alternatives rejected: a top-level `retry` object (retry is an execution-behavior fact and lives where `chunk_rows` and `batch_count` already do); recording only the attempts a retry followed (drops the final failure, so the entry count would understate the tries by one and the exhausted story would end mid-sentence); per-attempt timestamps (duplicate what `timings` and `delay_before_retry_ms` state, at the cost of nondeterministic report content); bumping `report_version` (additive fields do not change how existing readers parse the report).
