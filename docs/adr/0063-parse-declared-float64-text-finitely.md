# Parse Declared Float64 Text Finitely

Declared `float64` coercion accepts only text that parses to a finite IEEE double; text spelling a non-finite value — `NaN`, `inf`, `Infinity`, and their case variants that Rust's `f64` parser admits — fails coercion and becomes a `type_coercion_failed` Rejected Record like any other misfit. This closes an asymmetry: inference has refused to observe non-finite text as `float64` since the finite guard of issue #23, but a field declared or overridden to `float64` still coerced `"NaN"` successfully, so a load could land NaN in DuckDB today and would hand SQL Server — whose `FLOAT` holds only finite doubles — a value it cannot store at all. The guard lands at exactly one site, the CSV coercion path: JSONL `float64` coercion accepts only JSON numbers, and JSON cannot express a non-finite number, so every other route was already closed.

This is deliberately a shared-pipeline rule, not a SQL Server accommodation. The Rejected Record contract stays destination-independent — the same source records survive or reject regardless of where the load points — which is the same principle ADR-0062 applies from the other side when it keeps destination representability limits out of record-level semantics. Non-finite text in business data is near-always a quality incident, and surfacing it as a Rejected Record at parse — counted against the Reject Threshold, written to the load artifact — tells the operator which records and why, where a destination write error would report only that a chunk failed. The cost is a behavior change judged a bug fix in the spirit of the inference guard: a CSV load that today lands NaN in DuckDB through a `float64` override will instead reject those records. The alternative — keeping the permissive parse and letting non-finite values become SQL Server write failures — was rejected because it forks record-level outcomes by destination: the identical record would survive into DuckDB but kill a chunk on SQL Server, making load results a function of the connector rather than of the data and the chosen schema.
