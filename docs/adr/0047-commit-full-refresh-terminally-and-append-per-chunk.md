# Commit Full Refresh Terminally and Append Per Chunk

Chunked execution (ADR-0045, ADR-0046) gives every load a commit rule per load mode. **Full refresh keeps a single terminal commit boundary regardless of chunk count**: the Parquet session writes all chunks into its staging directory as one part file each and performs the established single rename; the DuckDB session wraps the replace in an explicit transaction — `BEGIN`, `CREATE OR REPLACE TABLE "<dataset>" AS SELECT * FROM arrow(?, ?)` for the first chunk, one `INSERT` per remaining chunk, `COMMIT` — the multi-statement moment ADR-0030 explicitly anticipated, preserving its Atomic Commit posture across chunks. Any failure before the terminal commit leaves the destination untouched. **Append commits per chunk**: the Parquet session stages and renames one complete part per chunk, and the DuckDB session runs one auto-committed `INSERT ... BY NAME` per chunk, so a failure after k committed chunks leaves exactly that prefix visible, traceable through the load id and report — ADR-0021's append posture at chunk granularity, and the commit boundary retry work will build on. All four atomicity/strategy report facts stay byte-identical: `best_effort`/`staging_then_replace`, `best_effort`/`staged_part_append`, `atomic`/`transactional_replace`, `best_effort`/`insert`.

The report tells this story honestly with `report_version` unchanged. `execution.batch_count` means "chunks the destination committed": a single-chunk success still reports `1`, and small-load reports stay identical to before apart from the additive `execution.chunk_rows` echo (ADR-0046) and per-run identifiers and timings. The write phase begins when the destination session opens: a failure opening it — `begin` itself failing, before any record batch was exchanged — keeps the pre-write posture, exactly as the same destination-preparation failures reported before sessions existed. A failure after the session opened reports `execution.record_format: "arrow_record_batch"` and the committed chunk count: `0` for a full refresh before its terminal commit, `k` for an append after `k` chunk commits, and the full count in the post-commit boundary case (a close failure after DuckDB's `COMMIT` succeeded), with `row_counts.written` and the failure's written-records fact counting committed records the same way. All other failures before the write phase keep the established `"not_started"` / `0` posture unchanged. A destination-changing failure reports the mode's write facts even when the failing operation itself is source-side — an append abandoned by the ADR-0045 mutation guard after committed chunks reports `best_effort` with its strategy, never `not_applicable` — while an abandoned session that committed nothing keeps `not_applicable`.

Alternatives rejected: per-chunk commits for full refresh (breaks the mode's replace-completely-or-not-at-all meaning and would surface half-replaced datasets to readers); a staging table plus terminal swap for DuckDB append (append is documented best-effort per ADR-0021, and per-chunk commits are precisely the boundary retry needs); renaming `batch_count` to `chunk_count` (a report-reader-visible break for zero information gain — the field's meaning is documented instead); bumping `report_version` for the additive echo and the honest failure posture (additive fields and a strictly more truthful failure posture do not change how existing readers parse the report, matching the ADR-0030 precedent).
